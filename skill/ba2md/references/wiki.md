# 消费 wiki（桥梁）

Wiki 是需求与项目之间的第一座桥（SUMMARY）：这个项目是什么、边界在哪、当前架构怎么切、这条需求落在哪一刀、术语怎么对齐。精确当前标识进 draft 时再从 `sources/<id>` 锚。

源码调研是同一座桥的加深。找到一个 owner 不算走完：待定、可能相关的源也要先读它的 wiki 再判断；相关的进调研。完成条件见 SKILL 节点 2。

本文件是节点 2 的单源：主干读什么、怎么 grep、怎么顺藤摸瓜、如何判断邻仓、何时停。

## 树

跑 `ba2md discover --json`。每个 `wiki/<id>/` 的组织结构是 `tree`。树上没有的路径不打开。根是具体的 `wiki/<id>/…`。

`tree` 已经是目录。碰到 `index.md` / `index.mdx` 只收链接，不通读。

## 主干

树上有才打开。按文件名 stem 或中文别名匹配。缺了记 GAP，继续走。

| 角色 | 匹配 |
|------|------|
| 总览 | `overview`、总览、概述 |
| 架构 | `architecture`、架构 |
| 源码归属 | `source`、`sources`、源码 |

同层有多份则都读。子目录里的同名页：需求或已读主干点名了该子树再打开。

## Grep 与顺藤摸瓜

1. 从需求抽关键词（系统名、能力、对象、接口），加上主干里刚读到的术语。
2. **每个**已挂载 `wiki/<id>/` 下搜文件名和正文。不用 `wiki/**`。有命中才消费那棵树。
3. 打开有用的命中。沿 markdown 链接走到树上存在的邻页；需要上下文时再打开所在子树的总览/架构。
4. 一页与需求和已建落点都无关，停这条藤。不要把所有命中读完。

已读页或需求点名的邻仓，即使这次 grep 没命中，只要它有 `wiki/<id>/`，也要按主干 + grep 读完再判断。

## 判断每条源

可能相关 = 需求点名、已读 wiki 点名（上下游、事件、共享数据、鉴权、被调用），或能对上 discover 的 `sources/<id>`。不要把工作区里每个源都过一遍。

| 判断 | 含义 | 下一步 |
|------|------|--------|
| owner | 拥有本需求 | 调研 |
| 相关 | 在路径上 | 调研 |
| 无关 | 落点之外 | 排除 |
| 待定 | 读过对应 wiki 仍不清，或没有 wiki | 节点 3 |

相关不是 maybe。不要在只锁定 owner 之后把邻仓丢掉。

## 停

`research-plan.md` 能写清 **项目是什么**、**这条需求落在哪 / 不落在哪**，并且每个可能相关的源都有上表判断（待定须写已读哪份 wiki，或无 wiki）。列出一个 owner 就停，不算完成。

## 写入 research-plan

- 项目理解（依据总览 / 架构 / 源码归属，缺则 GAP）
- 需求落点（子系统 / 边界 / 当前缝，依据哪些已读页）
- 实际打开过的路径
- 词表（有则记）
- 候选源：每条 `sources/<id>` + 判断 + 依据

无 wiki：把 GAP 写进项目理解，源定位交给节点 3。主干都缺：仍用 grep 建落点。

## 谁读

每个需要判断的 `wiki/<id>/` 都要读。一份：主会话。两份及以上：每个 wiki 一个子代理，交回项目理解 + 需求落点 + 该 wiki 上的源判断。子代理不写 `research-plan.md` / `progress.yaml`。主会话合并后写盘。
