# 消费 wiki（桥梁）

Wiki 是需求与项目之间的第一座桥（SUMMARY）：这个项目是什么、边界在哪、当前架构怎么切、这条需求落在哪一刀、术语怎么对齐。精确当前标识进 draft 时再从 `sources/<id>` 锚。

源码调研是同一座桥的加深，不是这一步的目标。候选仓可以顺手记下；定位确定则节点 3 不问。完成条件见 SKILL 节点 2。

本文件是节点 2 的单源：主干读什么、怎么 grep、怎么顺藤摸瓜、何时停。

## 树

跑 `ba2md discover --json`。每个 `wiki/<id>/` 的组织结构是 `tree`。树上没有的路径不打开。根是具体的 `wiki/<id>/…`。

`tree` 已经是目录。碰到 `index.md` / `index.mdx` 只收链接，不通读。

## 主干

树上有才打开。按文件名 stem 或中文别名匹配。缺了记 GAP，继续走。

| 角色 | 匹配 |
|------|------|
| 总览 | `overview`、总览、概述 |
| 架构 | `architecture`、架构 |
| 源码归属 | `source`、`sources`、源码 |

同层有多份则都读。子目录里的同名页：需求或已读主干点名了该子树再打开。

## Grep 与顺藤摸瓜

1. 从需求抽关键词（系统名、能力、对象、接口），加上主干里刚读到的术语。
2. 在该 `wiki/<id>/` 下搜文件名和正文。不用 `wiki/**`。
3. 打开有用的命中。沿 markdown 链接走到树上存在的邻页；需要上下文时再打开所在子树的总览/架构。
4. 一页与需求和已建落点都无关，停这条藤。不要把所有命中读完。

## 停

`research-plan.md` 能写清 **项目是什么** 和 **这条需求落在哪 / 不落在哪**。列出仓名、或把关键词命中读完，都还不够。

## 写入 research-plan

- 项目理解（依据总览 / 架构 / 源码归属，缺则 GAP）
- 需求落点（子系统 / 边界 / 当前缝，依据哪些已读页）
- 实际打开过的路径
- 词表（有则记）
- 候选源（副产品：每条依据 + 确定/不确定）

无 wiki：把 GAP 写进项目理解，源定位交给节点 3。主干都缺：仍用 grep 建落点。

## 谁读

一份 `wiki/<id>/`：主会话读完。

两份及以上：每个 wiki 一个子代理，交回项目理解 + 需求落点 + 候选。子代理不写 `research-plan.md` / `progress.yaml`。主会话合并后写盘。
