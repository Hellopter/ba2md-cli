# 3.x.2.2 Frontend Page Design · Conditional

Resolve this section in the Template Coverage Plan before deep research.

## Relevance Rule

- `RELEVANT`: the requirement changes user-visible frontend behavior or a selected frontend project pair owns affected pages, routes, components, or client state.
- `UNKNOWN`: the requirement suggests frontend impact but project discovery has not yet found or excluded a frontend pair; create a bounded discovery unit.
- `NOT_APPLICABLE`: the requirement has no frontend impact and no selected frontend project pair exists.

For `NOT_APPLICABLE`, do not create frontend research units or populate a frontend design body. Keep the heading blank, write a concise N/A reason, or omit it only as the active template permits.

## Evidence Rules

- Support current pages, routes, components, state, fields, and interactions only with VERIFIED FACTs.
- When a matching frontend pair exists, inventory every affected page, route, component, state transition, field, and interface dependency required by the change.
- When the requirement affects frontend behavior but the repository lacks matching Sources, record GAP; do not fabricate or ask the user to guess.
- When requirement prose defines target behavior, write an explicit PROPOSAL without presenting it as current implementation.

## Suggested Output Coverage

As applicable, cover every in-scope page/entry point, state and interaction, field and validation, permission, interface dependency, error response, compatibility concern, and instrumentation item. Trace each to the Implementation Inventory and evidence/claim IDs.

## Quality Gate

- The Template Coverage Plan supports the section's relevance classification.
- A backend-only requirement with no frontend impact does not contain frontend design content.
- Every precise current identifier has a VERIFIED anchor.
- Every in-scope frontend inventory item appears in the draft or has an explicit exclusion reason.
- Missing material is GAP rather than fabricated content or user guesswork.
